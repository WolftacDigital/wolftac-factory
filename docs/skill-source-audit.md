## Scope and accounting contract

Each stage table aligns procedure sections by meaning, not diff hunk positions. `S-`, `B-`, `R-`, and `I-` identify spec/build/review/integrate rows; `A-` identifies reference assets. A row may own disjoint ranges when a surface places the same section in different positions. The machine-readable [ledger](skill-source-audit/ledger.json) records every exact source interval, quote, decision and reason.

Every physical line, including common text, blank lines, headings and frontmatter, belongs to exactly one row. This deliberately stronger coverage rule means any diff algorithm and any pair of copies can be traced without depending on canonical being correct. The verifier independently discovers the source set at the pin and re-runs all pairwise Git diffs. An insertion or deletion maps on the side where that line exists; absence is recorded in the row’s presence column, not assigned a fictitious line.

**Decision semantics:** `shared` means the behavioral section belongs in core or a task-triggered shared asset. Equivalent wording, line wrapping, numbering and provider tool names may remain rendering parameters; these do not create different behavioral policy. `platform-only` means an actual loader/runtime/host capability overlay, not simply “only Hermes currently has it.” `stale` means remove only after the listed replacement and conflict approval. Each row has a proposed decision now; unresolved conflicts are separately marked, not disguised as a fourth decision category.

`missing/extra` is a coverage asymmetry, not an instruction to drop the longer copy. `wording/adapter` identifies aligned sections with surface/presentation differences; it does not claim byte equality. `conflict` points to the explicit question list. SECURITY tags are conservative, derived from the source section’s credential/approval/secret language, and require manual review.

## Proposed source layout

```text
skills-src/
  <stage>/
    core.md                       # shared behavioral sections and named slots
    frontmatter/<surface>.yaml     # SKILL.md loader/argument metadata, no policy
    frontmatter/plugin/agents/openai.yaml # separate native-plugin sidecar (S/B/R)
    platform/<surface>.json        # exact named-slot text / adapter bindings
    manifest.json                 # outputs, required slots, row IDs, assets
  assets/spec/spec-template.md     # canonical template content + approved Q1 adapter
  assets/<stage>/scripts/          # unchanged shared executable assets
  assets/<stage>/references/       # task-triggered shared reference assets
  assets/capabilities/<host>/      # Windows/WSL/runtime-specific recipes
```

Proposed marker syntax: a whole line `{{overlay:<name>}}`. Expansion is literal UTF-8/LF text, not template evaluation or shell interpolation. Every used marker must exist exactly once in that surface’s overlay map; unused or unknown markers fail closed. No executable expressions or secret/env interpolation. Tool names, report-agent labels, loader metadata, supported transport and native-path syntax are explicit surface bindings. An overlay may not override an approval, credential or stage-authority restriction.

The manifest emits each plugin sidecar to `plugins/wolftac-factory/skills/wolftac-<stage>/agents/openai.yaml` unchanged apart from explicitly approved future metadata edits. It never concatenates the sidecar into SKILL.md. Spec template sections come from the canonical template asset, rendered externally for C/P and inline for D/X/H, with all S-template-* safeguards retained and Q1 resolved explicitly.

Core owns semantic ordering. Use row-derived anchors such as `B-claim.before`/`B-claim.after` in the final layout. Shared assets have explicit trigger/link metadata; package validation checks every linked target and retains the full approved asset inventory. Frontmatter may be a dedicated first slot (as in this example) or the separate YAML files shown above; it must not be parsed and reserialized in a way that loses invocation fields.
