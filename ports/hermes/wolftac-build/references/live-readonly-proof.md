# Proving read-only behavior against an active source tree

## Retained scheduler incident evidence

- Copy only the explicitly authorized output/state files into profile scratch before analyzing a historical incident. Inventory retained coverage and report gaps; current state is a current snapshot, not proof of historical values.
- Convert scheduler output filenames from their verified local timezone to the issue's requested UTC window before filtering or counting. Persist extracted lane decisions and aggregate them programmatically. Distinguish successful process dispatch, scheduler run confirmation, worker success, and issue pickup; none proves the next by itself.
- Preserve the original fingerprint/comment window when adding a broader eligibility read. Keep extra paged comments in a separate field and test that paging cannot change the old fingerprint, while an older park still suppresses timed retries.

- Do not count a before/after hash mismatch as proof the application wrote files. Active schedulers and retention can legitimately change the same tree during the observation.
- Do not waive differences merely because their paths resemble scheduler files or their mtimes fall inside the process lifetime. Require evidence sufficient to attribute or exclude the tested process for every relevant difference.
- Treat Windows GetProcessIoCounters as supporting evidence, not full path attribution. WriteTransferCount can be compared with captured stdout/stderr bytes, but process totals do not identify paths and do not establish ownership of rename/delete/metadata operations or mapped writes.
- Record exact executable/head, process lifetime, before/after counts, changed/removed/added relative paths, read errors, exclusions, counters and pipe bytes. Never print source contents or read secret/auth/token files to manufacture complete coverage.
- When the latest interruption already establishes that the only remaining work needs unavailable tracing capability, run the read-only capability preflight before claiming. If capability and the Linear work order are unchanged, do not reclaim merely to repeat successful synthetic tests or post an identical interruption. Treat the candidate as not completable under the completion-budget gate, continue checking other eligible candidates, and apply the scheduled run's nothing-new suppression only if no actionable dirty-worktree finding or other new result exists.
- Preflight tracing capability before repeating an expensive live comparison: check current-token elevation and Performance Log Users membership, native Windows privileges, available trace tools, and existing recording status. A non-elevated token and no usable trace are a capability blocker, not a reason to elevate or install drivers autonomously. In Git Bash environments call `$env:SystemRoot\System32\whoami.exe` explicitly from PowerShell; bare `whoami.exe` may resolve to the MSYS binary and reject `/priv`. Report bounded tool searches as bounded, never as proof that a tool is absent machine-wide.
- Resolve the existing native Bun executable from a verified prior harness or filesystem lookup rather than assuming `.bun/bin` or PATH; npm-installed Bun can live under `AppData/Roaming/npm/node_modules/bun/bin/bun.exe`.
- Use only an allowlisted environment and Bun --no-env-file for credential-free live-reader probes. Bound worker-owned test servers with cooperative stdin shutdown; do not stop live services to make inventories stable.
- Keep filesystem APIs and application behavior unchanged during observational proof. Label instrumentation and fixture evidence accurately; interception alone is not an uninstrumented OS trace.
- When the only review defect is missing live attribution, do not send the issue back to review with another equivalent incomplete hash run. Record an interrupted build with the new evidence, return the claim cleanly, preserve unfinished work, and identify the required path/process tracing capability. Do not install tracing drivers, elevate, or change auditing/runtime configuration without authorization.
